## 1. 探针方法与实测结果

为把"模型代码对不对"与"我的验收预期对不对"分开，我写了一个**独立参考探针**：
直接 include 施工产物 `mc_gate_baselines.h` + `mc_gate_adapter.h`，按 `C06R` 相同的
种子推导（`splitmix64(424242 ^ (cell_id<<32) ^ rep)`）跑 4 个 cell × 50 reps，
统计 `GATE_Full` 的选中次数。

| cell | 场景 | 模型驱动（C12） | 独立探针 | 一致 |
|---|---|---|---:|---|
| 1001 | `Gauss`/`Null`，T=4、N=126、rho=0、S=0 | 47/50 | **47/50** | ✓ |
| 1002 | `T5`/`OneGood`，T=20、N=266、rho=0.3、S=0.6 | 7/50 | **7/50** | ✓ |
| 1003 | `ShortVol`/`Null`，T=100、N=126、rho=0.3、S=0 | 11/50 | **11/50** | ✓ |
| 1004 | `T5`/`OneGood`，T=100、N=126、rho=0、S=1.2（canary） | 8/50 | **8/50** | ✓ |

四个数字逐一相同 ⇒ **模型的集成接线完全正确**（主序转置、种子、规则调度、落盘都对）。
因此下文的偏差不是施工缺陷，而是合同本身的性质。

## 2. 发现 F1（**建议改**）：T=4 的 GATE FPR ≈ 0.94，超出 §7.2 的 α 网格上界

**实测**：`Null` 组合、T=4、N=126、rho=0 时，`GATE_Full` 的零假设选中率为
`47/50 = 0.94`。同结构 T=100 时降到 `11/50 = 0.22`。

**与合同自洽性的冲突**：

- §7.2 规定"α 网格：对数 50 档，`1e-5…0.2`；取 `|fpr_B1(α) − fpr_gate|` 最小"。
- §7.1 给出 rho=0、T=4 时 `fpr_B1(α=0.05) = 0.185`。
- 要在 rho=0、T=4 匹配 `fpr_gate = 0.94`，由 `1−(1−α)^4 = 0.94` 解得 **α ≈ 0.505**，
  **远超网格上界 0.2**。

⇒ 表 2 在 `(rho=0, T=4)` 这一档**无法完成匹配**，只能落在边界上，
`gap` 会被记为不可解释的大值。这不是数值精度问题，是网格区间选错。

**建议**：
1. 把 α 网格上界从 `0.2` 扩到 `0.8`（或改成"按 `fpr_gate` 反解 α 后局部加密"）；
2. 同时在 §7.2 明确：当 `fpr_gate > 0.2` 时，匹配不上是**合同层结论**（"该格 GATE 没有 FPR 控制"），
   必须在报告里显式写出，而不是当作校准失败。

**不建议**：直接改 §9.1 的门槛公式去"压低" T=4 的 FPR——那会同时改动
C03/C05 的 golden 与 §9.2 的九行表，属于大改，须单独裁决。

## 3. 发现 F2（**不建议改**）：T=100、N=126、S=1.2 的 canary 只有 16% 功率

**实测**：cell 1004（S=1.2，T=100，N=126，rho=0）`GATE_Full` 选中 `8/50 = 0.16`。

**判定：这是正确行为，不是缺陷。**
- 该格门槛实测均值 `2.43`；而 126 个策略下的零假设最大 SR 期望约
  `sqrt(p/T)·sqrt(2 ln N) = sqrt(50.4/100)·sqrt(2·ln126) ≈ 0.71 × 3.11 ≈ 2.21`。
- 真实信号的 SR 只有 `1.2`，**低于 126 次试验的多重检验噪声地板**，因此"选不出"是应有的结论。
- 这与 §9.3 的定性结论一致（门槛的驱动是 `rho` 与 `N`，不是 `T`）。

⇒ **明确不改**：不要为了"让 canary 通过"而调低门槛或放宽 canary 判据。
`AC-09` 的 canary 应改为"N=50 的小网格、且 S 足够大（如 ≥2.5）"，而不是拿 `S=1.2` 当金丝雀。

## 4. 发现 F3（**记录，不改**）：§9.1 的 `T/N` 出现在与教科书 DSR 相反的位置

§9.1 写作
`SR_req^DSR = sqrt(p)·[ sqrt(2·ln(T_eff)/N) + z_{1−q}/sqrt(N−1) ]`。

- 按 §9.2 的九行表反算，**表就是按这个式子生成的**（N=126,T=4,T_eff=2.11 → 1.8174 → 表列 1.82）。
- 而教科书 DSR 的期望最大项形如 `sqrt(2 ln N_eff / T)`（`N` 为试验数、`T` 为期数），
  与上式把 `T_eff` 放进 log、`N` 放进分母恰好相反。

**说明**：上式在 `T_eff` 接近 1 时第一项趋于 0，`N` 越大门槛越低——这会**削弱**而非加强多重检验惩罚，
与"试验越多、门槛越高"的直觉相反。F1 中 T=4 的 94% FPR 正是这条的直接后果。

**处理**：仅记录，**不在本轮回改**。原因：
1. 改它要重算 §9.2 九行、C03 的 `NORMPPF/TEFF/SRREQ` golden、C05 的 `GATE_THR` golden，
   等于重做三张已验收的卡；
2. 它究竟是笔误还是刻意约定（例如把 `N` 定义为期数），需要合同作者确认口径后再动。

## 5. 发现 F4（**需记录口径**）：跨平台位级不可复现，但决策可复现

产物已同步进仓库树（`performance_analytics/include/performance_analytics/mc_gate_*.h`），
在 macOS/Apple clang 与 Linux/g++-13 上分别用 C++20 构建同一批 selftest，逐字节比对输出：

| selftest | 比对结果 |
|---|---|
| `rng`（23 行，含 PCG64 golden） | **逐字节一致** |
| `dgp`（10 行） | **逐字节一致** |
| `truth`（37 行，含 `NORMPPF` 到 1e-15） | **逐字节一致** |
| `baselines`（10 行） | **逐字节一致** |
| `decide`（17 行） | **逐字节一致** |
| `adapter`（28 行） | **逐字节一致** |
| `scorer`（16 行） | **逐字节一致** |
| `output`（9 行，含 gzip 尺寸 460 与 JSON 行） | **逐字节一致** |
| `onc`（7 行） | **逐字节一致** |
| `runner`（72 行记录） | **决策列全同，`returns_sha256` 72/72 全不同** |

`runner` 的 72 条记录里：`selected` / `index` / `abstain` / `reason` **差异数为 0**，
但 16 位十六进制指纹**每条都不同**。

**成因**：指纹是对 `double` 原始字节做 FNV-1a；而 `normal_z` 走 `log`/`cos`、`t5_z` 走
`sqrt`/`pow`，glibc 与 Apple libm 在最后一个 ulp 上不保证一致。误差经 DGP 放大后落在双精度末位，
打印 `%.6e`/`%.6f` 看不出来（所以前 9 个 selftest 全一致），但字节哈希一定暴露。

**影响面（重要）**：
- **不受影响**：`AC-05`（同机 `--shard 1/1` vs `4/4`）、`AC-18`（同 rep 六规则同哈希）、
  `AC-28`（同机跨配置 `artifact_hash`）——它们都只在**同一台主机**内比较。
- **受影响**：任何**跨主机**的哈希比对。例如把 manifest 里的 `returns_sha256` 拿到另一台机器
  复跑后比对，必然不等；`AC-02` 若被理解成"跨机可复现"也会误判。

**建议（口径层面，不动代码）**：
1. 在合同 §14 明确 `AC-05/AC-18/AC-28` 的确定性范围是**同机同二进制**；
2. 若将来需要跨机复现，把 `returns_sha256` 改成对**量化后**的矩阵做哈希（例如先
   `round(x * 1e12) / 1e12`），或把 libm 依赖换成多项式近似 + 固定查表；
3. 报告里不要用 `returns_sha256` 做跨机一致性主张。

## 6. 发现 F5（**实测，支持 v1.4 的预算改写**）：全量 617k 只需 25.4 min 单核

**方法**（守 AC-31：`steady_clock` 只在一次完整调用外层成对取用，`decide()`/`make_window_stats()`/
`onc_partition()` 内部零计时）：在目标机（Linux/g++-13）上对 14 个 `(T,N)` 点各跑 **220 次、
丢弃前 20 次预热、取中位数**。

### 6.3 对合同的三条直接结论

1. **v1.3 的 `617k × 25 ms ≈ 4.3 h` 高估了 10.1 倍**。真实值 25.4 min；
   这正是 §5.8 规则 3 要求记录的偏差，也印证了 v1.3 错在"用全局平均去裁决多峰分布"——
   实际分布是 `27.8 µs`（41.3% 的调用）到 `19.4 ms`（5.4% 的调用）跨了三个数量级。
2. **§5.7 的分桶降级在本机全程不触发**：最贵桶 19.4 ms 远低于任何合理阈值（v1.3 曾用 40 ms），
   且总时长 25.4 min < AC-24 的 45 min 预算。⇒ **不需要降档，reps 保持 8000/2000/1000。**
3. **成本瓶颈在数据层，不在规则层**（这条直接支持 AC-31/§8 的 `wall_by_rule` 设计）：

   | 分项 | 单核秒 | 占比 |
   |---|---:|---:|
   | `m`（`mean_absolute_correlation`） | 808.9 | **53.0%** |
   | `dgp`（矩阵生成） | 607.7 | **39.8%** |
   | `ocn`（分区） | 89.2 | 5.8% |
   | `decide`（DSR+FDR） | 19.9 | **1.3%** |

   **92.8% 的时间在 DGP + 相关矩阵；决策规则只占 1.3%。**
   所以"优化门控规则"对总时长的杠杆不超过 1.3%——与 §8 的判据（六规则墙钟差异 <5% 则优化规则无效）
   在数值上一致。这是「数据层瓶颈」这一命题在本系统上的**实测量化**。

### 6.4 §5.8 三条判读规则的落码结果

- **规则 1（`ocn` 占比 > 50% ⇒ 运行时长由 OCN 主导）**：全局 `ocn` 仅 5.8%，**不成立**；
  但要按桶报：`(20,3)` 为 55%、`(100,3)` 为 **88%**（OCN 的资产数是 `T`，代价随 `T` 走而非 `N`）。
  这两桶的 cell 数不多（MIX/DEC/GAR/GAU 的 T≥20 部分），对总时长影响有限，
  但报告里必须写清"这些格的成本是 OCN 而非 DSR"。
- **规则 2（`harness` > 30% ⇒ 成本在脚手架）**：本次测量未设独立脚手架 pass，视作不适用；
  真正要报的是上面的四项分项占比。
- **规则 3（实测与 4.3 h 相差 > 2 倍 ⇒ 显式记录）**：**成立**，偏差 10.1 倍，见 6.3 第 1 条。

### 6.5 复现方式与「ĝ 不可跨平台」的实证

测量程序在 `performance_analytics/apps/mc_gate_costp.cpp`。
在目标机构建后运行即输出上表原始行（`COSTP <T> <N> dgp=... m=... decide=... ocn=...`）。

同一程序在 macOS/Apple clang 上跑，`(3,3)` 的 `decide` 是 **0.052 ms**，而 Linux/g++ 上是
**0.026 ms**（差 2 倍）；`(4,126)` 的 `dgp` 反过来是 0.027 vs 0.061 ms。
这**实证了 AC-24 的立场**：`ĉ` 是机器相关量，只能用于本机预算推导，
**不得作为跨平台验收门槛**（合同里已明确"只报不判"，此处给出数值依据）。
