## 1. 文章讲了什么，以及它到底管不管这个实验

文章的核心事实链：

```text
分区太细（每 symbol 每月一个文件）→ 69.9 万文件 × 341µs 固定开销 = 238s
  → 数据层供给被钉死在 51k 行/s → 引擎 700 万行/s 无法兑现（利用率 0.7%）
```

**它的适用边界是 Parquet 数据湖链路。** MC-GATE-VALIDATION 的链路是：

```text
PCG64 → 合成收益矩阵 R(T×N) → 门控调用 → 决策落盘
```

**不读湖、不经过 DuckDB/Arrow、不进 cpp_engine 主循环。** 因此：

- P0（压实 69.9 万文件）对本实验**零收益**。为了让 MC 实验跑快先去压实数据湖，是纯粹的错误排序。
- 文章里 51k 行/s、17.9 MB/s、341µs/文件 这些数字，**不能**用来给本实验估算任何成本。
- 文章的 §九（两条独立路径逐位一致）恰好印证本合同 AC-12 / AC-28 的方法学是对的，无需改动。

**但是**，文章有三条**可迁移**的诊断纪律，v1.3 违反了两条。这才是要修的地方。

## 2. 必须修（4 处：口径与纪律）

### R1 —— 预算用单一平均数代替分布（对应文章教训一、三）

**现状**（§5.2 / §5.7 / AC-24）：

```text
617k × 25ms ≈ 4.3h 单核      # 平坦单价
若实测单次 >40 ms，整体降为 4000/1000/500   # 全局平均阈值触发全局降级
```

**缺陷**：按 §5.1 网格实际清点，调用成本跨了两三个数量级：

| 调用类别 | 次数 | 占比 | 代表成本 |
|---|---:|---:|---|
| `N=3`（ALT/MIX/DEC/NEG/GAR/GAU） | 255,000 | 41.3% | 微秒级（`correlation_matrix` 3×3、OCN 3 点、DSR N=3） |
| `N≥126`（NUL/FRQ/SVL/BYA/RET/ABL/SWP） | 362,000 | 58.7% | 毫秒级起（T=100 时 `correlation_matrix` 100×100×N + OCN 4×≤100 迭代） |

平坦单价同时造成两个方向的错误：

1. **错配**：把 41% 的预算分给最便宜的 255k 次调用（实际可能是全部成本的 0.1%）。
2. **误触发**：§5.7 的 `>40ms` 是对**全局平均**的判据。若真实分布是"均值 6ms、但 T=100 那 10.6 万次是 40ms"，平均只有 12ms —— 降级不会触发；反之若均值刚好压线，降级会连带砍掉本不需要降的廉价格。

这正是文章"批 p50 只有 21 行 / 1.2KB"的反面：**不要用一个平均数描述一个多峰的分布**。

**修法（v1.4）**：

- 新增强制 pilot **`COSTP`**：在 D1 实测每类 `(T,N)` 的单次成本 ĉ(T,N)（≥200 次取中位数，去掉首次预热），建立成本模型。
- 总预算 = `Σ_cells reps × ĉ(T_cell,N_cell)`，**由 config 推导**（AC-01 的"不得硬编码"因此自动成立）。
- 降级阶梯改为**按格类触发**：只有 `ĉ > 阈值` 的格类降 reps，`N=3` 类保持原 reps 不动。
- AC-24 的 `单次 T=100,N=520 ≤100 ms` 是**机器相关**的绝对量，改为"报实测值 + 由实测推导总时长 ≤ 预算"。

### R2 —— 在决策热路径内插桩会污染被测量对象（对应文章教训二）

**文章实测**：Arrow 桥接层"每行两次 `steady_clock::now()`"，把 55% 的引擎内部成本记到了"解码"头上。这是**测量本身改变了被测对象**的教科书案例。

**v1.3 的风险**：harness 要产出 `teff_measured`、`m_measured`、成本剖面、AC-24 的计时，天然会在门控调用附近计时。若在 `decide()` 内或每次门控调用处成对取时钟，对微秒级的 `N=3` 格是**数量级级别的污染**（一次 `steady_clock::now()` 约 20–30ns，成对 ~50ns；而 3×3 格单次可能只有 5µs → 1% 尚可，但若逐 rep 内层再取就不可接受）。

**修法（v1.4）**：新增 AC ——

- 计时**只允许**在 `(cell_id, rep_id, rule_id)` 粒度取一对时钟，`decide()` 与库函数调用内部**零计时**。
- 成本剖面在**独立 pass** 测（可与 `OCNP` 复用同一遍遍历，但不得与正式决策 pass 混跑）。
- `metrics.json` 增列每规则墙钟时间（`wall_by_rule`），使"供给受限"类退化可诊断：若六条规则墙钟时间几乎相同，成本在共享 harness（DGP + `m` + OCN），不在规则。

### R3 —— 解析门槛需与实测零分布并列（不改判据）

§9.2 的门槛表我逐行验算过，**数值是对的**（`sqrt(p)*[sqrt(2ln T_eff/N)+z_{1-q}/sqrt(N-1)]`，p=50.4：N=126/T=4 → 1.8175，rho=0/N=266/T=20 → 1.6584）。所以这里**不是勘误**。

问题是：解析式是**渐近**的（§9.3 自承"比教科书 DSR 多罚约 0.6 个 t 单位"），而本实验跑完 617k 次会**免费产出经验零分布**。文章的方法学要求"单一来源的性能数字永远可疑、多路径互证"。

**修法（v1.4）**：解析门槛**仍作判据锚**（不自我评分），但报告必须并列 `E[max SR]` 的实测零分布分位数；偏差 > 0.05 SR 时记 `analytic_threshold_drift` 并说明方向。

### R4 —— 数据层边界必须写进合同（防误用）

文章的 P0 结论是**性能工作里最容易被误用的一条**。合同里若不写清，后续很容易出现"为了让 MC 实验跑得更快，先去压实数据湖"这种把 4.3h 的事拖成几周的事故。

**修法（v1.4）**：新增 §1.2「数据层边界声明」：

- 本实验为纯合成 DGP，**不经数据湖、不经 `cpp_engine` 主循环**；2026-09-11 报告的 P0/P1/P2/P3 结论对本实验的运行时无影响。
- 若 §15 D9 的 Tier B 需要喂真实收益，则**继承**该报告的约束（实测 51,216 行/s 供给速率、引擎利用率 0.7%）；Tier B 的可行性前提是先完成 P0 压实。合同须在 Tier B 立项时重估预算。

## 3. 必须修（2 处：可复现性硬缺口）

### R5 —— PCG64 的"种子→状态"与"状态→输出"从未钉死

AC-06 要求"自实现 PCG64 + 前 1e6 输出自检"，AC-14 要求跨语言（C++ ↔ Python 标准库）逐位一致。但合同**从头到尾没写播种约定**。没有它：

- AC-06 的"自检"没有参照物；
- AC-14 的 `|ΔSR|≤1e-12` 无法建立（两个实现各自 seed 出不同流，一切都不一致）。

这是"验收标准在逻辑上不可能通过"级别的缺口，而不是风格问题。

**修法（v1.4）**：在 §3.1 钉死（我已用它跑通逐位一致的实现，见 §4）：

```text
状态推进:  state ← state·MULT + INC   (mod 2^128)
MULT   = 0x2360ED051FC65DA4_4385DF649FCCF645
INC    = 0x5851F42D4C957F2D_14057B7EF767814F
播种:  state=0; inc=(seed<<1)|1 (mod 2^128); step(); state+=seed; step()
输出:  old=state; step(); xs=(hi^lo)&(2^64−1); out=rotr(xs, hi>>58)
       ← 注意是 ROTR（右旋），不是 rotl
golden(seed=42): 3eb27489f5ff73e0 287472e87ff5705a bbd190b04ed0b545 b6cee3580db14880
                 bf5f7d7e4c3d1864 734eedbe7e50bbc5 a5b6b5f867691c77 6d6d2656235610ad
golden(seed=12345): 78861cdd32fcc735 d11b1d37bff50104 92e63e7ae540560c c8c14150ef8defaf …
```

> 附带实测陷阱：`(1<<128)-1` 在 C++ 里是未定义/报错（移位计数 ≥ 位宽）。128 位乘法自然溢出**就是** mod 2^128，不需要掩码。这条必须写进合同，否则每个实现者都会踩一次。

### R6 —— 路径引用：一条误报，一条真缺口，一条施工前置条件

**误报（我一开始判错了，此处更正）**：`portfolio_math/apps/formal_oos_driver.cpp:39` **是存在的**——
本地权威树里该文件第 39 行确实是 `constexpr double kPeriodsPerYear = 50.4;`。我先前在远端
`/mnt/fdisk/quant/quant-backtester-cpp` 上 `ls portfolio_math/apps` 报"不存在"，是因为**远端检出是旧树**
（HEAD `4f9b0be`，本地 `9f4ca0e`，且远端连 `9f4ca0e` 这个 commit 对象都没有）。所以 §1/§17 的该引用
**有效，不改**。

**真缺口**：`performance_analytics/apps/` 在**两棵树里都不存在**。合同 §13 把
`performance_analytics/apps/mc_gate_validation.cpp` 当既有路径写，实际是本实验**新建**目录，
需同步 `performance_analytics/CMakeLists.txt`。同时 `phase4b_governance_reference.cpp` 实际位于
`performance_analytics/tests/`（§1 引用时未给目录，容易找错）。

**施工前置条件（比路径本身更重要）**：远端检出落后于本地权威树且缺 `portfolio_math/apps/`。
**在任何施工开始前，必须先把远端同步到本地 HEAD**，否则本地模型会在缺文件的老树上施工，
AC-28（`G_full` 逐位等于真实门控）与 §1 的引用核对都会失败——这不是合同缺陷，是环境缺陷。

**修法（v1.4）**：§13 标注 `performance_analytics/apps/` 为新建；§17 补全 `tests/` 目录；
**新增 §15.0 施工前置**：远端树必须与合同 `git_commit` 一致，否则拒绝开跑。

## 7. 一句话

文章的结论不是"去压实数据湖"，而是**"先算清楚时间花在哪一段，再决定动谁"**。v1.3 把这句话写给了数据层，却没写给自己：它的预算是照抄来的平均数，它的计时会污染被测量对象，它的 RNG 没有参照物。

**修这六处，不改一个判据。**
