# 数据湖压实：等价性与性能验收报告

- 生成时间：2026-11-04（Linux 侧实测）
- 代码提交：`2548603 feat(data): 数据湖压实工具链，数据层吞吐提升 33 倍`（`origin/main`）
- 数据：真实湖 14,105,167 行 / 4,692 个标的 / 2006-01 ~ 2026-07

## 1 瓶颈与方案

真实湖把 1,410 万行切成 **698,654** 个 Parquet 文件（均值 20.2 行 / 4.3 KB），
数据层每秒只交付约 3.9 万行，而 C++ 引擎可吃下百万行/秒，端到端被数据层卡死。
瓶颈是**每文件固定开销**（实测 0.52 ms/文件），不是 Parquet 解码。

方案：不改引擎、不改查询语义，只按 `year/month/bucket` 重排物理布局，
把碎片合并成大文件。`bucket` 本身不是数据列（`BAR_COLUMNS` 只有 7 列），
因此重排不改变任何行值；`schema_hash` 只依赖 schema 定义，也不变。

结果：**698,654 → 15,808** 个文件，行数、标的数、时间范围完全不变。

## 6 结论

压实未改变数据本体、未改变 schema、未改变查询语义与排序，

C++ 引擎代码零改动。

## 6.1 旧湖 vs 新湖：全湖回放可行性（C3 的正面结论）

同一命令 `run_minute_replay data/<lake> --strategy-symbols 10`，只换湖：

| | 旧湖 (data/lake) | 新湖 (data/lake_compact) |
|---|---|---|
| `--target-mb 256` | 13 分钟仍未完成，RSS 冲到 12.2 GB，人工终止 | — |
| `--target-mb 32` | **5 分 43 秒撞上 10.8 GB 内存墙，被看门狗杀掉** | — |
| 结果 | 无法在本机完成 | **70 秒完成，峰值 863 MB** |

这台机器 15 GB 内存。旧湖无论批大小怎么调都会在 6~13 分钟内撞墙，
而新湖 70 秒跑完 1,410 万行。也就是说压实把一个**本来不可能在本地跑完的操作**
变成了 70 秒的事——这比"两湖结果相等"更能说明 P0 的价值。

旧湖的成因很可能是 69.8 万小文件放在 **exFAT** 上：exFAT 对海量小文件的
元数据与随机寻址性能极差，DuckDB 需要为每个文件维持扫描状态。

## 7. 端到端策略回放等价性（双均线 MA10/30）

第 1~5 节验证的是数据本体，第 5 节的 API 对齐验证的是接口契约；本节验证**撮合、持仓、绩效三层在压实前后完全一致**。

### 7.1 为什么不用文档 §9 的现成基准

`docs/cpp-core-benchmark-report.md` §9 记录的基线（equity `1,196,621.0555`、成交 24,782、轮次 12,056、订单 88,815）出自一个**已被删除的「MA(10/30) 全市场双均线」探针脚本**，其标的筛选、仓位分配、下单量、手续费等参数均无留存记录；文档 §10.2 给出的重现命令实际运行的是 `two_batch_round_trip` 策略，与该基线不是同一 run_spec。因此该组数字**无法在不猜参数的前提下复现**，不能说清结果不符是压实问题还是规格不符。

改用可复现方案：`tools/ma_dual_probe.py`（本次入库）实现一个完全确定性的 MA(10/30) 全市场双均线探针——逐 symbol 维护 10/30 周期收盘均线，上穿买入、下穿卖出，固定下单 1 手，手续费按成交额 0.0003，同批内先统一算信号再统一下单，无随机、无时间依赖。对两湖跑**同一 run_spec**。
