# C++ 回测核心（cpp_engine）评测报告与优化方案

- 评测日期：2026-09-11
- 被测对象：`quant-backtester-cpp` 主分支（含工作区未提交改动）构建的 `cpp_engine` pybind11 扩展 v0.3.0（Release）
- 驱动方式：PythonProject 平台 Python 驱动层（`python.engine_api`，`QBT_BACKEND=cpp`），仅测 C++ 核心链路，不含 Python 平台自身回测功能与 Dashboard
- 代码变更：无（评测全程未修改两个仓库的任何代码；评测产物已按约定清理，本报告除外）

## 0. TL;DR

| 结论 | 证据 |
| --- | --- |
| C++ 引擎本体性能优秀：**700 万行/秒** 综合吞吐，逐截面延迟 p50 0.65ms（对象 API）/ 0.92ms（流式引擎间隙），延迟分布紧（p95/p50 ≈ 1.5） | 全湖 14.1M 行引擎内部仅 2.0s（解码 1.10s + 撮合执行 0.91s） |
| **全系统瓶颈不在 C++ 核心，而在数据层**：引擎能吃 ~700 万行/s，实际只被喂 ~5.1 万行/s，差距约 **135 倍** | 端到端 277s 中引擎仅占 0.7%；根因是 69.9 万个平均 4.3KB 的小文件 |
| 双执行路径**逐位一致**：对象 API 与 Arrow C Stream 跑同一策略，权益精确到分相同、轮次相同（12,056） | 2024–2026 窗口探针 B/C 对比 |
| A 股微观结构规则建模正确且经受了压力：88,815 笔委托中 63,916 笔被正确拒绝（T+1 可卖约束为主） | 策略回测探针 |
| 最优先优化是**数据层文件压实**（P0），预期端到端 **15–25 倍**提升；其次桥接层列式解码与策略回调列式接口（P1） | 详见第 8 节 |

## 1. 评测范围与方法

### 1.1 被测链路

```text
数据湖(Parquet) → DuckDB/Arrow 扫描 → PartitionAwareIterator(有序截面)
    → Arrow C Stream / pybind11 对象 API → cpp_engine(撮合/持仓/绩效) → Python 策略回调
```

`cpp_engine` 核心模块：`engine.cpp`（主循环，1538 行）、`order_book.cpp`（撮合）、`position.cpp`（T+1/公司行动）、`pnl_tracker.cpp`（绩效）、`arrow_bridge.cpp`（C 流桥接，327 行），合计约 3.6k 行 C++20。

### 1.2 环境与数据

| 项 | 值 |
| --- | --- |
| 平台 | Apple Silicon（arm64），macOS 25.4.0 |
| Python | 3.9.13（PythonProject .venv） |
| 扩展 | cpp_engine 0.3.0，Release，`cpp_engine.cpython-39-darwin.so` 1.3MB |
| 数据湖 | 2.9GB，**698,654 个 Parquet 文件**，14,105,167 行，约 2,500+ 标的 |
| 数据形态 | 日线（每标的每交易日一条，时间戳为上海 15:00 收盘），2006-01-04 → 2026-07-22，共 4,991 个交易日截面 |
| 截面宽度 | 全湖均值 ~2,826 只/截面；2024 年后窗口均值 ~3,879 只/截面 |

> 注：benchmark 框架命名 "minute replay"，但当前湖内实装数据为日线。引擎与数据频率无关，各项延迟按截面宽度（行数）线性伸缩，可外推到分钟线场景。

### 1.3 测量方法

1. **分阶段基准**（项目自带 `python.benchmarks.run_minute_replay`，全湖无过滤）：依次测量存储裸读、Arrow 解码、Arrow 纯计算、C 流回放、事件回放、策略回测六个阶段，每阶段记录耗时、行/字节吞吐、RSS、批延迟分位数。
2. **自研细粒度探针**（2024-01-01 → 2026-07-23 窗口，2.39M 行、617 个截面）：
   - A：对象 API 逐截面 `process_market_data_batch`（无策略）延迟分布；
   - B：对象 API + 双均线策略回调（返回 `Order` 对象）延迟分布与结果；
   - C：`process_arrow_stream` 一次灌入 + 零拷贝 `MarketBatchView` 回调，用回调间间隙估计引擎逐截面处理延迟；
   - D：`finalize` 后各指标查询耗时；B/C 结果一致性校验。
3. **引擎内部计时**：`process_arrow_stream` 返回 `decode_seconds` / `execution_seconds`（C++ `steady_clock`），用于把引擎耗时从端到端耗时中剥离归因。

### 1.4 局限性声明

- 每阶段单次运行，未做多轮方差统计；但两条独立路径测得的数据层供给速率高度一致（全湖 51,216 行/s vs 2024+ 窗口 50,423 行/s），结果稳定可信。
- 缓存状态 `uncontrolled`（无 cold/warm 控制），首轮存储读含冷缓存效应。
- 策略回测使用简单双均线策略（短 10 / 长 30，100 股整手，万三佣金），用于压测引擎路径，不代表策略研究结论。

## 2. 端到端分阶段结果（全湖 14.1M 行 / 69.9 万文件 / 4,991 截面）

| 阶段 | 耗时 | 吞吐 | 备注 |
| --- | ---: | ---: | --- |
| storage_io（存储裸读） | 118.7s | 17.9 MB/s | 698,654 个文件逐个打开，均值 ~170µs/文件 |
| arrow_decode（DuckDB 扫描） | 239.0s | 59,020 行/s | 700,094 个批；**批 p50 仅 21 行 / 1.2KB**，批延迟 p50 0.23ms / p95 0.48ms；均值 ~341µs/文件 |
| arrow_compute（Arrow 纯计算对照） | 1.09s | 420 万行/s | 热缓存下 `pc.sum` 采样 |
| **c_stream_replay（引擎，1 次流调用）** | 277.2s | 50,879 行/s | **引擎内部：解码 1.10s + 撮合执行 0.91s = 2.01s，仅占 0.7%** |
| event_replay（逐截面流调用 ×4,991） | 275.4s | 51,216 行/s | 引擎执行 1.05s；逐截面调用开销相对一次灌入可忽略 |
| strategy_backtest（含 Python 回调） | 272.4s | 51,780 行/s | 引擎执行 5.43s（4,991 次回调，每次下 10 笔订单） |

**核心归因**：端到端 277 秒中，C++ 引擎本体仅 2.0 秒（noop）/ 5.4 秒（含 Python 回调），其余 ~272 秒（98–99.3%）消耗在引擎上游的数据层——69.9 万个小文件使 DuckDB 逐文件扫描（每文件 ~341µs 的打开/footer 开销）和存储裸读（17.9 MB/s，NVMe 能力的约 1/100）成为绝对瓶颈。**引擎综合吞吐 7.0M 行/s（解码+执行）vs 数据层供给 51k 行/s ≈ 135 倍差距。**

## 3. C++ 核心细粒度延迟（2024–2026 窗口：2.39M 行、617 截面、均值 3,879 只/截面）

| 路径 | p50 | p95 | p99 | max | 折算吞吐 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 对象 API 逐截面摄入（无策略，含 pybind11 对象数组转换） | 0.65ms | 0.95ms | 1.32ms | 51.4ms（首调预热） | ~500 万行/s |
| 流式路径引擎逐截面处理（回调间间隙，含下单/成交/逐日估值） | 0.92ms | 1.53ms | 1.37s* | 1.50s* | ~420 万行/s |
| 纯 Python 策略回调体（view 逐标的访问 + 信号 + 建 Order） | 4.30ms | 4.87ms | 5.11ms | 6.28ms | — |
| 对象 API + 策略（单截面端到端） | 7.03ms | 10.33ms | 21.28ms | 138.9ms | — |

\* p99/max 尖刺来自 Arrow reader 供数卡顿（DuckDB 读取下一窗口），不是引擎开销——数据层瓶颈即使在流式过程中也会以"停顿"形式漏进来。

**引擎内部吞吐分解**：

- noop 全湖回放：执行 0.91s / 14.1M 行 ≈ **1,540 万行/s**（~183µs/截面）；
- 含策略流式回放：执行 2.92s 中约 2.60s 是 Python 回调体，引擎自身 ≈ 0.31s → **~770 万行/s**；
- 解码：全湖 1.10s（~780ns/行），占引擎内部总时间 55%。

## 6. 优点

1. **核心吞吐与延迟达到"研究平台够用、准生产可用"水平**：700 万行/s 综合、1,540 万行/s 纯撮合，逐截面延迟亚毫秒且分布紧凑；按 65ns–240ns/行的区间线性外推，全市场分钟线（~5,000 标的 × 240 bar/日）单日约 1.2 亿行的引擎内部耗时约 8–17 秒，README 声称的 120 亿行设计容量对应纯引擎时间约 20–30 分钟量级——引擎不是容量瓶颈。
2. **双入口 + 零拷贝设计成熟**：Arrow C Stream 直接消费 capsule（GIL 释放、RAII 守卫、支持涨跌停/停牌/整手/复权/因子暴露等 15 个可选列），对象 API 面向事件驱动嵌入；`set_on_cross_section_view` 让 Python 策略零拷贝读截面，且实测与对象路径结果逐位一致。
3. **正确性工程化**：严格输入校验快速失败、异常后防污染、截面原子可见（成交完成后策略才看到截面，杜绝半截面泄漏）、NEXT_OPEN/CLOSE 两种成交时点、T+1 按上海日界滚动可卖量、涨跌停阻断、成交量参与率上限、整手与资金约束、公司行动分数股校验——保守建模且无前视偏差路径。
4. **可复现性内建**：单线程确定性、增量式绩效指标（O(1) 查询）、benchmark 框架自动记录数据血缘（catalog generation、dataset/query 指纹、schema hash、后端制品 SHA-256）。
5. **轻量与边界清晰**：核心 3.6k 行、wheel 1.3MB、无重依赖；ML/实盘模块默认编译隔离；工程注释（中文）解释语义取舍。

## 7. 问题与风险（按严重度排序）

1. **[P0] 数据层小文件使引擎速度优势完全无法兑现**：69.9 万个文件（均值 4.3KB、20.2 行/文件），磁盘 ~206 B/行（理论 56 B/行的 3.7 倍，其中 parquet footer 等开销估计占 25–35%）；DuckDB 扫描 59k 行/s、裸读 17.9 MB/s。**按当前速率，120 亿行设计容量端到端需要约 65 小时，而纯引擎只要 ~25 分钟。**
2. **[P1] 桥接层逐行解码**：`decode_row` 每行构造 `MarketSnapshot` 且 symbol 每行一次 `std::string` 分配、每行两次 `steady_clock::now()` 计时；解码占引擎内部时间 55%。
3. **[P1] 策略回调是回放真实瓶颈**：纯 Python 策略使逐截面成本 0.65ms → 7.03ms（~11 倍）；零拷贝 view 仍需逐标的虚调用（~3,900 次/截面 ≈ 4.3ms）。订单侧已支持列式 dict 返回，但**输入侧没有列式（numpy）接口**，重型策略（如横截面 ML 推理前的特征组装）会先撞上 Python 墙。
4. **[P2] 引擎无内部并行**：单线程确定性是对的，但参数扫描/多组合只能多进程（每进程 ~1GB 稳态 RSS），无 native 批量回测入口。
5. **[P2] 构建分发摩擦**：目标环境需自备 cmake + pybind11 本地编译（~5 分钟）；macOS 部署目标告警；制品构建配置只能启发式推断（"Release wheel default (unverified)"）。
6. **[P3] 语义易用性**：无预检 API（如 `can_sell`）；EXPIRED 语义（跨 bar 滚存市价单的过期口径）需要读源码才能确认；拒单原因虽有 `reject_reason` 但缺少便捷的聚合统计入口。
7. **[P3] 数据层峰值内存**：DuckDB 解码阶段 4.1GB 峰值对大湖是隐患（可通过减小窗口/limit 内存缓解，但会进一步拖慢扫描）。

## 8. 优化方案

### P0 —— 数据层文件压实（收益最大，建议立即做）

**现状证据**：一个 Parquet 文件 ≈ 一个 symbol-月（20 行）；批 p50 21 行/1.2KB；每文件 ~341µs 扫描开销；~700k 文件。

**方案**：
1. 新增 compaction 工具：按 `(year, month, bucket)` 将 64 bucket 分区内的小文件合并为**每月每 bucket 一个文件**（目标 row group 8–64MB，zstd + symbol 字典编码），产物写入新 catalog generation，原分区保留为历史版本（符合 README"修订新建版本、不覆盖主键"原则）。预期文件数 700k → **~16k**（21 年 × 12 月 × 64），再按需降到 ~250/年（月级不分 bucket，牺牲部分单标的查询裁剪）。
2. 压实后重写数据时按 `(timestamp, symbol)` 全序落盘，catalog 标记"预排序"标志，`PartitionAwareIterator` 可跳过每窗口的 `table.take` 全排序。
3. 可选：对合并后文件绕过 DuckDB，直接用 pyarrow dataset 顺序扫描（少一层查询引擎开销）。

**预期收益**：
| 指标 | 现状 | 压实后（预估） |
| --- | ---: | ---: |
| 文件数 | 698,654 | ~16,000 |
| 批 p50 | 21 行 / 1.2KB | 数万行 / 数 MB |
| 存储裸读 2.9GB | 118.7s（17.9 MB/s） | 2–4s（NVMe 顺序读，且压实后体积预计降 ~2.5 倍至 ~1.2GB） |
| 全湖扫描 | 239.0s（59k 行/s） | 6–15s（150–500k+ 文件数下降 44 倍 + 列式吞吐） |
| **全湖端到端回放** | **277s** | **~10–20s（15–25 倍）** |

**实施要点/风险**：压实工具需保证逐行内容与顺序不变（可复用现有 schema 校验与内容 hash 校验）；压实期间数据目录翻倍，注意磁盘余量；catalog generation 原子切换已有机制可复用。数据层属 Python 平台仓库，本仓库配合提供"预排序 + 压实后文件"的兼容性验证（现有 `test_backend_parity` 可扩展）。

### P1-a —— 桥接层列式解码 + symbol 字典化

**现状证据**：`arrow_bridge.cpp` `decode_row` 逐行构造快照；解码 1.10s 占引擎内部 55%。

**方案**：
1. symbol 列要求/优先使用 `dictionary<int32, utf8>`：解码时一次建 `字典索引 → SymbolId` 映射（`engine_common` 已有 `SymbolRegistry`），行内只做整数映射，消除逐行 `std::string` 构造；对非字典输入在批首构建 `string → id` 哈希缓存。
2. 数值列按缓冲区批量读取（`const int64_t*`/`const double_t*` 直接指针遍历），null 位图按 64-bit word 预判整段无 null 的快路径。
3. 去掉每行 `steady_clock::now()` ×2，改为每批计时后按行均摊，消除 ~40–60ns/行的固定开销。

**预期收益**：解码 1.10s → 0.2–0.4s（2.5–5 倍）；引擎内部总时间 2.0s → ~1.2s；在 P0 落地后此项将成为引擎内部主要成本，值得做。

**风险**：低——纯桥接层改动，`ArrowSchemaValidation` 已有严格 schema 校验兜底；需为字典编码列补 schema 校验分支与测试。

### P1-b —— 策略回调列式（numpy）输入接口

**现状证据**：view 回调逐标的 `symbol(i)/close(i)` 调用 ~4.3ms/截面；订单侧已支持列式 dict（`parse_batch_orders`），输入侧不对称。

**方案**：新增 `set_on_cross_section_arrays`：回调入参为 `{symbol_id: np.int32[n], close: np.float64[n], ...}` 的零拷贝 `py::array_t`（包装 `std::span<const MarketSnapshot>` 或独立列缓冲），策略用 numpy 向量化产出信号后按现有列式 dict 返回订单。保留现有 view/对象回调不动，三种接口并存。

**预期收益**：回调 4.3ms → 0.1–0.3ms/截面（10–40 倍）；全湖策略回测引擎执行 5.43s → ~1.5s；配合 P0 后策略回测总时间逼近纯数据扫描时间。对 ML 策略（特征矩阵化）收益最大。

**风险**：中低——新接口不破坏旧契约；需明确 symbol_id 与 symbol 字符串的映射查询 API（`get_symbol(id)`）以免策略侧再做字符串表。

### P2 —— 并行回测与构建分发

1. **多组合并行**：不动引擎单线程语义，在 Python 层提供多进程池驱动（每进程一个 engine + 参数集）；建议单进程独占 1–1.5GB 内存预算。可另提供 native "批量回测"入口（一次 Arrow 流喂 N 个引擎实例副本，C++ 层 N 路撮合），收益是省去 N 份数据解码。
2. **发布 Release wheel**：cibuildwheel + CI（macOS arm64/x86_64、manylinux），终端用户免 cmake；`.so` 内嵌 git SHA + 版本号，`_backend_environment` 的构建配置推断可从"启发式"升级为"精确读取"。
3. **内存**：数据层扫描窗口已可调（`target_bytes`），建议 DuckDB 连接设置 `memory_limit` 并在文档中给出"窗口大小 × 并行度"的内存预算公式。

### P3 —— 语义与易用性

1. 预检 API：暴露 `can_sell(symbol, qty)` / `sellable_quantity` 便捷查询，减少策略侧无效委托（本测试中 72% 委托被拒即源于此）。
2. 文档化 EXPIRED 口径（跨 bar 滚存市价单的过期条件）与 `FillTiming` 语义矩阵。

### 10.3 指标口径

- "引擎内部耗时"：`process_arrow_stream` 返回的 `decode_seconds + execution_seconds`（C++ steady_clock 计时，不含 Arrow reader 供数等待）。
